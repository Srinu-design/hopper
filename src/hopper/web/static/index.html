Hopper

A job queue on PostgreSQL that doesn't lose jobs.

Send a job over HTTP. Hopper runs it at least once, retries it with backoff, parks it in a dead-letter queue if it keeps failing, and lets you replay it. Jobs run now, after a delay, at a set time, or on a cron schedule.

What it does

Everything a production job queue needs, each feature proven by a test. See the tests

  • One worker per job

    Workers claim rows with SKIP LOCKED, so no two ever get the same job.

  • Crash recovery

    A killed worker's jobs come back when its lease runs out and finish on another.

  • Fencing tokens

    A worker that was paused too long can't overwrite the newer run.

  • Retries with backoff

    Full-jitter exponential backoff, with limits set per task.

  • Dead-letter queue

    Jobs that keep failing are parked with their history, and can be replayed.

  • Idempotency keys

    A retried request returns the same job instead of creating a second one.

  • Delayed and cron jobs

    Run later, at a set time, or on a schedule. Two schedulers, never a double fire.

  • Many tenants

    Each tenant sees only its own jobs and has its own rate limit and queue quota.

  • Backpressure

    Over the limits, the API answers 429 or 503 with Retry-After instead of falling over.

  • Webhook jobs

    The http task calls your URL, signed, with an SSRF guard.

  • Metrics and alerts

    Prometheus metrics from every process, five alerts and a dashboard.

  • Safe deploys

    Every merge deploys itself; a bad release rolls back with no one involved.

It keeps going when workers die

Architecture

One image runs every role. Caddy is the only public entry point. The API, workers and schedulers keep no state of their own: PostgreSQL holds every job, and Redis holds only rate-limit buckets and a cached queue depth, so losing Redis loses no job.

Caddy
Reverse proxy. Spreads requests over both API replicas, checks their health every 2 s, and turns on HTTPS once a domain is set.
API × 2
FastAPI on uvicorn. Checks the API key, the tenant's rate limit and the queue depth, then writes the job row.
Workers × N
Claim up to 20 jobs each, run them, renew their leases every 10 s, then ack or nack.
Schedulers × 2
Fire cron schedules, reclaim expired leases, count queue depth and delete old jobs. Both run at once.
PostgreSQL 16
The queue and the source of truth. See Database.
Redis 7
Token buckets for rate limits and the cached queue depth. If it goes down, limits fall back to each API process.
Prometheus + Grafana
Metrics from every process, five alert rules and a read-only dashboard.
GitHub Actions
Tests every change, builds the image, and deploys every merge to main.

Database

PostgreSQL 16 is both the queue and the record. A job is one row in jobs, and every change to a job is one guarded UPDATE, so a job is never half-updated. The SQL is written by hand, and every migration works with the release still running.

How a worker claims jobs

One statement picks the next ready jobs and leases them. SKIP LOCKED makes other workers pass over rows being claimed instead of waiting, so each gets a different batch.

WITH next AS (
  SELECT id FROM jobs
  WHERE queue = :queue AND status = 'queued'
    AND run_at <= now()
  ORDER BY priority DESC, run_at
  LIMIT :limit
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs SET status = 'running',
  attempts = attempts + 1,
  lease_token = gen_random_uuid(),
  lease_expires_at = now() + interval '30 s'
FROM next WHERE jobs.id = next.id
RETURNING ...

Indexes that stay small

Each hot index is partial, so it holds only the rows it serves, however many finished jobs pile up.

  • jobs_ready_idx: queued jobs by queue, priority and time, for the claim
  • jobs_lease_idx: running jobs by lease end, for the reaper
  • jobs_dead_idx: dead jobs per tenant, for the dead-letter queue
  • jobs_idem_uidx: unique idempotency key per tenant
  • schedules_due_idx: enabled schedules by next run, for cron

Finished jobs are deleted after 7 days, and jobs is vacuumed after 2% of its rows change instead of the default 20%.

The life of a job

  1. Enqueued

    The API checks the key, the rate limit and the queue depth, then inserts a queued row, to run now or later.

  2. Claimed

    A worker takes it with SKIP LOCKED and gets a 30 s lease and a fresh lease token.

  3. Running

    The worker renews the lease every 10 s. If the worker dies, the lease runs out and the reaper puts the job back.

  4. Done or retried

    Success: succeeded. Failure: back to the queue after a backoff, or dead after the last attempt.

  5. Replayed

    A dead job keeps its id and history. Replay puts it back with a fresh set of attempts.

When things break

Delivery is at least once: if a worker dies at the wrong moment, a job can run twice, but an accepted job is never lost. Exactly-once is impossible when workers can crash, so handlers are written to be safe to repeat.

Security

API keys
32 random bytes. Only a prefix and an HMAC-SHA256 hash with a secret pepper are stored, and keys are compared in constant time.
People
Passwords hashed with Argon2id. Logging in gives a 15-minute token, and login attempts are rate-limited per email.
Tenant isolation
The tenant comes only from the key, and every query filters on it. Another tenant's job answers 404, so ids never leak.
Webhook jobs
Private and internal addresses are refused, even through DNS tricks, and every call is signed so the receiver can check it.
Abuse limits
A rate limit per tenant, queue quotas, and request bodies over 256 KB refused.
The server
Only Caddy has public ports. Secrets live in a mode-600 file on the host, never in the image or the repository.

Operations

Watching it

  • Every process exports Prometheus metrics: enqueues, runs by outcome, queue depth and wait, lease losses, HTTP latency.
  • Five alerts: QueueBacklog, HighFailureRate, DLQGrowing, NoWorkers, NoScheduler.
  • A read-only Grafana dashboard anyone can open.
  • JSON logs, each line carrying the request id, which follows a job from the API to its worker.

Shipping it

  • Every pull request runs lint, type checks, the tests and a full deploy rehearsal.
  • A merge to main builds one image and deploys it to the EC2 host.
  • The deploy migrates, replaces the API one replica at a time with no downtime, then smoke-tests a real job.
  • If anything fails, the old release comes back by itself. The drill: caught at 42 s, serving again at 79 s.

Known limitations

  • One host: no high availability, and backups are not automated yet.
  • Plain HTTP on this server until it has a domain: use only throwaway demo keys here.
  • No fairness between tenants: rate limits cap what each sends, but workers pick by priority and age.
  • About 35 s to recover a crashed worker's job (lease plus reaper interval).

How to use it

Hopper is an HTTP API. Every call under /v1 carries a tenant's API key, and the tenant always comes from the key, never from the request. The test suite runs every example from step 3 on against a real server, so they work as written.

1Point at the server

The examples use two shell variables. The first is this server's address:

export HOPPER_URL=http://localhost:8000

2Get an API key

A tenant's owner logs in and creates a key. The full key is shown only once, and Hopper stores only a hash of it.

# log in as the tenant owner (the token lasts 15 minutes)
curl -X POST "$HOPPER_URL/auth/token" \
  -H "Content-Type: application/json" \
  -d '{"email": "ops@acme.example", "password": "<owner password>"}'

# create a key with the access_token from that answer
curl -X POST "$HOPPER_URL/admin/api-keys" \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "my app"}'

Then keep the key field from the answer in the second variable:

export HOPPER_API_KEY=hop_live_...

On this demo server, tenants and owners are created by the operator. It runs on plain HTTP, so the key crosses the network unencrypted: use a throwaway demo key.

3Enqueue a job

Name a task and give it a payload. The answer is 201 with the new job.

curl -X POST "$HOPPER_URL/v1/jobs" \
  -H "Authorization: Bearer $HOPPER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"task": "sleep", "payload": {"ms": 500}}'
{"id": "0f8c2d4e-…", "task": "sleep", "queue": "default", "status": "queued",
 "attempts": 0, "max_attempts": 5, "run_at": "…", "attempt_history": [], …}

Keep the id: the next examples use it as $JOB_ID.

4Check on it

One job, with its result or error and every attempt (which worker ran it, when, and how it ended):

curl "$HOPPER_URL/v1/jobs/$JOB_ID" -H "Authorization: Bearer $HOPPER_API_KEY"

Or a list, newest first. Filter by status or queue; pass next_cursor back as cursor for the next page.

curl "$HOPPER_URL/v1/jobs?status=succeeded&limit=10" -H "Authorization: Bearer $HOPPER_API_KEY"

5Run it later, or cancel

Give delay_seconds or a run_at time, at most 30 days ahead. A run_at in the past simply runs now.

# in 30 seconds
curl -X POST "$HOPPER_URL/v1/jobs" \
  -H "Authorization: Bearer $HOPPER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"task": "sleep", "payload": {"ms": 100}, "delay_seconds": 30}'

# at a set time, in any time zone
curl -X POST "$HOPPER_URL/v1/jobs" \
  -H "Authorization: Bearer $HOPPER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"task": "sleep", "payload": {"ms": 100}, "run_at": "2026-11-01T09:00:00+05:30"}'

A job that is still waiting can be cancelled. One that already started can't (409).

curl -X POST "$HOPPER_URL/v1/jobs/$JOB_ID/cancel" -H "Authorization: Bearer $HOPPER_API_KEY"

6Retry safely

A request can time out after Hopper already created the job. Send an Idempotency-Key, and a retry with the same key and body returns the same job (200, with Idempotent-Replayed: true) instead of creating a second one. The same key with a different body is refused (422).

curl -X POST "$HOPPER_URL/v1/jobs" \
  -H "Authorization: Bearer $HOPPER_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-42" \
  -d '{"task": "sleep", "payload": {"ms": 100}}'

Delivery is at least once: if a worker dies at the wrong moment, a job can run twice. Make handlers safe to repeat, for example by keying their side effects on the job id.

7Dead letters and replay

A job that keeps failing is retried with backoff. After its last attempt, or at once for a permanent error, it becomes dead. This one fails for good straight away:

curl -X POST "$HOPPER_URL/v1/jobs" \
  -H "Authorization: Bearer $HOPPER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"task": "fail_always", "payload": {"permanent": true}}'

List the dead-letter queue (filter by queue, task or since):

curl "$HOPPER_URL/v1/dlq" -H "Authorization: Bearer $HOPPER_API_KEY"

Replay one dead job now, with a fresh set of attempts:

curl -X POST "$HOPPER_URL/v1/jobs/$JOB_ID/replay" -H "Authorization: Bearer $HOPPER_API_KEY"

Or replay many at once (up to 1,000 per call), spread over a minute so they don't all land together:

curl -X POST "$HOPPER_URL/v1/dlq/replay" \
  -H "Authorization: Bearer $HOPPER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"filter": {"task": "fail_always"}, "spread_seconds": 60}'

8On a schedule

Five-field cron, in the schedule's own time zone. Two schedulers run, and a tick never fires twice.

curl -X POST "$HOPPER_URL/v1/schedules" \
  -H "Authorization: Bearer $HOPPER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "morning-report", "cron": "0 9 * * 1-5", "timezone": "Asia/Kolkata",
       "task": "sleep", "payload": {"ms": 10}}'

List them with GET /v1/schedules; turn one off with PATCH /v1/schedules/{id} and {"enabled": false}.

9From a program

The same calls from Python. This client retries on network errors, 429 and 503, waiting as long as Retry-After says. The idempotency key makes the retried enqueue safe. It needs pip install httpx.

import os
import time
import uuid

import httpx

client = httpx.Client(
    base_url=os.environ["HOPPER_URL"],
    headers={"Authorization": f"Bearer {os.environ['HOPPER_API_KEY']}"},
    timeout=10,
)


def call(method, path, **kwargs):
    """One API call, retried on network errors, 429 and 503."""
    for attempt in range(5):
        try:
            response = client.request(method, path, **kwargs)
        except httpx.TransportError:
            time.sleep(2**attempt)
            continue
        if response.status_code in (429, 503):
            time.sleep(float(response.headers.get("Retry-After", 1)))
            continue
        if response.is_error:
            raise RuntimeError(f"{method} {path}: {response.status_code} {response.text}")
        return response.json()
    raise RuntimeError(f"{method} {path}: gave up after 5 tries")


# One key for this job, reused by every retry, so it is created only once.
job = call(
    "POST",
    "/v1/jobs",
    json={"task": "sleep", "payload": {"ms": 500}},
    headers={"Idempotency-Key": f"report-{uuid.uuid4()}"},
)
print("enqueued", job["id"])

while job["status"] in ("queued", "running"):
    time.sleep(0.5)
    job = call("GET", f"/v1/jobs/{job['id']}")

print(job["status"], job["result"] or job["last_error"])
